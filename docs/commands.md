# The commands

Every command is installed as `ml-stack-<command>` and answers as `ml-stack <command>` too;
both spellings run the same code, so `ml-stack-bench sweep` and `ml-stack bench sweep` are one
command.

| | |
| --- | --- |
| `ml-stack-gym catalogue\|run\|train\|evaluate\|replay\|export` | `catalogue` reports native dependencies for MetaDrive driving, RWARE warehouse robots, SUMO-RL traffic and integrated traffic-driving. `run ENV --controller CONTROLLER --config JSON` records native observations, actions and rewards with manual, random or decision-model control; `train ENV --timesteps N` trains a CPU PPO policy in the cache, and `evaluate ENV CHECKPOINT --episodes N` measures it on separate seeds. `replay TRAJECTORY` reads recorded transitions; `export TRAJECTORY REVIEWS OUTPUT` exports reviewed action labels as decision-model Case JSONL. Install the matching `gym-driving`, `gym-warehouse`, `gym-traffic` or `gym-rl` extra and the documented pinned MetaDrive source for driving; the app's Gym view provides live controls, native camera and sensor scenes, and episode review. |
| `ml-stack-models find <words>` | search the Hub for a model, unsloth first; `files <repo>` lists the quantisations and prints the `hf:` reference to serve each; `card <repo>` reads the sampler settings its publisher recommends; `layout <model>` prints the attention layout off a GGUF header -- which layers hold a full cache, slide, recur or share it, plus experts, indexers and lookup tables |
| `ml-stack-serve fit` | how many people fit at a given context, and the longest context one person can have -- from **measured** per-model KV numbers, not a formula: `--measure` serves a model once at `-lv 4` and records what llama.cpp says it allocated; `--room 24G` asks about a machine that is not this one; `--per-user N` sets the contexts in the table; `--plot FILE.png` draws who fits against the context and what the memory costs as the users arrive, with the familiar card sizes behind it, so a large model with a tiny cache can be seen overtaking a small one with a fat cache; `--write FILE` writes the Markdown; `--ui` puts the same two panels up as an interactive page on loopback (also the app's **Fit** view) |
| `ml-stack-serve limits [--memory 90G] [--servers N] [--slots N] [--idle 10m]` | how much of this machine ml-stack may take, written down once and read everywhere: the memory cap rides on `hub.room`, so every preflight, fit and lease honours it without being handed it; the server and slot caps refuse a lease **before** a process is started, naming what to stop or what to raise; `--idle` is what `reclaim` and the fleet daemon act on. Every limit is off until one is set, so a machine nobody has told anything about behaves exactly as it did; `--clear` takes them all off |
| `ml-stack-serve reclaim [--idle 10m] [--watch]` | stop the model servers nobody is using, so the memory they hold goes back. Idleness is **asked** of each server (`/slots`) rather than remembered, since a written-down 'last used' is only as good as every caller remembering to write it and an adopted server has no caller here at all; a server that does not answer is left alone, and a long single answer is never mistaken for idleness. What each look found is kept, so idleness adds up across looks and a pass can act on what the daemon has been watching -- but only over intervals short enough to be an observation: a gap in the looking is a gap in the evidence, and a pass after a silent afternoon reports nearly nothing and stops nothing |
| `ml-stack-serve status\|up\|down\|profile\|build\|escalate\|memory` | one model per port, in one shape; refuses a mismatched lease; announces to the fleet; `--draft auto` and `--mmproj auto` find the speculative head and the vision projector shipped with the weights; `--spec` chooses draft or n-gram guessing; every start writes the server's own output to a log of its own under `~/.ml-stack/logs` (the last five per port are kept); `status` names that log, the head each running server was started with and the share of its guesses the model is keeping, and with nothing serving, the log the last server on the port wrote; `profile` prints the shape a model measured best in for each workload -- asking, ingesting or chatting -- and `up --profile --workload WORKLOAD` fills every flag not given from that record; `build` compiles or downloads a current llama-server and switches to it once verified, so a release lagging master by an architecture is a permanent fix rather than a one-off `--binary`; `escalate --add N` grows a running server's slots in place, carrying its conversations over; `memory` says how much a model may use here and `--persist` makes that survive a reboot |
| `ml-stack-serve leases\|history [--model NAME] [--since 3d]` | every lease records why it was taken (`up --for TEXT`, `$ML_STACK_LEASE_FOR`, or the program's own reason), who took it, the process chain that started it, its working directory, git worktree and branch; `leases` lists each server's holders with all of it, `status` shows it beside each lease and names the other holders of an adopted server, and `history` lists the leases that have ended |
| `ml-stack-bench prepare\|run\|sweep\|drafts\|concurrent\|show\|report` | time and score a graph's answers — wall clock, calls, cached tokens against read ones, KV cost, draft acceptance, and how much of the expected answer was shown; `show --rates` adds accuracy per second, per 1k tokens and per GB with the Pareto frontier, `--plot` draws it; `report` composes every run, every draft head and the measured memory into one document per model, ending in the line to serve it by (`--text`, `--md FILE`, `--room`, `--at`). `--on NAME=URL` measures a server somebody else started -- a llama-server by `http://`, Ollama by `ollama://host:port/model`, an OpenAI-style server by `openai://host/model` -- and every run records what served it (program, version, format, runtime, quant), the process tree's resident peak sampled every second, and None rather than 0 for any figure that program does not report; `sweep --no-draft` serves a model in the settings it scored best with minus the head, `--serve-label` names the runs |
| `ml-stack-bench queue FILE` | an evening of measurements as a file rather than the ninth zsh script of the night: one `ml-stack-bench` line per step, `#` comments, `set VAR=` with `${VAR}`, and `smoke:`/`then:` pairs where a failed smoke skips the run it guards and says so; every line is checked against the parser before the first model loads (`--dry-run` prints the plan), `--yes` and `--ceiling` are given once at the top, `--resume` skips what the store already holds since the queue started, `--detach` puts the whole evening in one background log and `status` says which step is running and what is left. Each step is its own process, so it takes the measuring lock itself and two steps never share the GPU |
| `ml-stack-draft MODEL` | what a draft head is worth for one model, measured rather than argued: it finds the head the model ships, picks the workload (the graph questions, or `--for ingest DOC.pdf --chapter N` to read a document), checks nothing else holds this machine and refuses if something does, then serves the model once per arm -- no head at all, then the head at each depth -- and prints them side by side: written tokens a second, acceptance, tokens per verification pass, the share of generation time spent drafting, milliseconds per drafted token and wall clock, each with the direction that is better. The last line is the `ml-stack-serve up` to paste, or the case for serving no head. `--draft-kv` adds an arm per cache type for the head's own KV cache; `--anyway` measures on a busy machine and marks every row as taken on one |
| `ml-stack-claude [MODEL] [--role R] [-- claude args]` | Claude Code on a model this machine serves (default Qwen3.8-27B-UD-Q4_K_XL, 262,144 tokens on one slot, q8_0 KV cache): the lease is taken, every model variable names the served alias, the window and auto-compact size are set to what is served, telemetry and betas a local server lacks are off, and the server goes when claude exits. A PreToolUse hook sends every tool call through the destructive-action classifier under the role (`read-only`, `approve-first`, `plan-and-go`) and asks in the Requests inbox; the settings file sits outside the working tree. The session is minted a workspace identity on the project's board and revoked on exit. `--on URL` talks to a server as it stands; the served model's own chat template is rewritten first |
| `ml-stack-codex [MODEL] [--role R] [-- codex args]` | Codex on a model this machine serves, the default coding harness: the same lease, window, role hook and workspace seat as `ml-stack-claude`, with a private `CODEX_HOME` holding the provider (`/v1/responses`), the context window, the role's sandbox and approval mode and the hook. `launch_coding_agent(model, role, project, harness)` in `ml_stack.coding` is the same for a program |
| `ml-stack-agent "task" --model MODEL` | one agentic task through the Claude Agent SDK (the `claude` extra) on the same lease; prints what it said and what it spent. `ml_stack.harness.session()` is the same for a program |
| `ml-stack-ingest DOCS --out STORE` | documents read section by section into one graph: chapters, sections, figures and key terms out of a PDF (`ml_stack.sources.pdf` -- the publisher's outline when there is one, the way the headings are set when there is not), each section through `Client.extract` against the document contract, folded per source with `entities.fold`, and written with the source, chapter, section and page behind every node; `--images` shows the model the figures, `--chapter` and `--sample` smoke it, `--detach` and `--resume` survive an evening, `status` says how far it has got, how fast the model is reading and writing, and how much of what the draft head guessed was kept, `ask` answers a question of the store so far, `--gold FILE` scores the extraction against passages with known triples (`--fail-under` makes that a gate), `retry` re-reads the units that gave up, and `forget` deletes the per-source reads kept in plaintext beside the store (`--source SLUG` for one) |
| `ml-stack-store check\|docs\|doc\|embed\|tidy` | what a graph store holds and whether it agrees with itself: `check` reads every document, node and edge by key and by scan and prints each disagreement (`--fix` rewrites a document a scan reads empty), `docs` lists the documents with their sizes, `doc PATH KEY` prints one as JSON (`--drop` takes it out), `embed --smooth N` spreads the vectors the store already holds over the graph so an entry with no text of its own is found by what its neighbours mean, and `tidy` runs the hygiene pass -- duplicates merged, inverses folded, doubtful labels flagged, conflicts, orphans and hierarchy cycles reported -- dry unless `--apply`; `--base-url URL` has a served model judge the names a spelling apart, the verbs in conflict and the doubtful labels from their passages, every verdict written to the store, `--rejudge` asks about every held verdict again, and `--gold` scores the judge against pairs whose answers are known |
| `ml-stack-world make\|questions\|simulate\|emit\|check` | an invented organised group -- company, community, university, open-source, nonprofit -- as a graph with people who could talk: `make` writes graph, personas and calendar from a seed; `questions` draws scored questions off its truth; `simulate` has the people talk for N working days, templated unless `--mix` hands a share of threads to a served model at `--model-url`; `emit` writes what was said the way Slack, a mail client, Teams or a scraper exports it; `check` reads an export back against its truth, holds its chain of command to a hierarchy with a top, and runs every generated name through the name detector |
| `ml-stack-security status\|events\|quarantine\|review\|scan\|baseline\|verify\|downloads\|hosts\|scanners\|sandbox\|unlock\|keystore\|keystore-reset` | what sentinel has seen and holds, each listing JSON with `--json`: `status` is the mode, counts by state, pins, decoys and whether the event log's hash chain verifies, and names what is held with the command that reviews it (`chip` is the same as a green, yellow, red or none mark); `review` is one screen of everything held with the reason in plain words, what it blocks and single keys to release one (`r`, `y`), stop watching every watched item (`R`), see details (`d`) or purge (`p`, id typed), for a person at a terminal; with no terminal it shows one dialog listing what is held with `Release`, `Keep held` and `Later` buttons, and `review --list\|--json` prints it anywhere; a quarantine that means something changed or was forged raises at most one such dialog at a time on the machine (everything held is in it, `Release` releases exactly what it lists), and anything else is shown by `status` and `chip` only; `ML_STACK_NOTIFY=off` shows no dialog; `events` reads the log; `quarantine list\|show ID\|add KIND:KEY` covers every kind of subject (messages, tool calls, tools, sessions, memory, models, artifacts, servers, MCP servers, credentials, peers) and `release ID`, `purge ID` and `mode` need a person at a terminal who types the id, and refuse when an agent started the process; `scan [--deep]` re-hashes every pinned file and checks the decoys, `baseline --pin FILE [--honey]` pins a file by digest and plants the decoys, `verify [--anchor LINE]` checks the log for edits, cuts and reordering; `downloads [--held] [--verify]` lists what came in from the internet with its source, hash and scan status, `hosts` and `approve-host HOST` show and extend the hosts that may be reached, `scanners` says which virus scanners this machine has, `scan-policy [CATEGORY ACTION]` shows or sets whether files nobody could scan are kept (the last two changes need a person at a terminal); `sandbox status\|test` names the backend that confines untrusted execution (and the deprecated tool behind it) and runs its guarantees against real confined processes, exit 1 when one fails `unlock` (a person at a terminal) makes the keystore's one master key and lets background processes read it, `keystore` prints whether it exists, any refusal and the operations this hour without touching the keystore, `keystore-reset` deletes it (docs/keystore.md) |
| `ml-stack-jobs status\|wait KIND\|stop KIND` | the long commands this machine has recorded -- a detached bench sweep, an ingest reading documents -- with the pid, the argv and the log of each: what is running, blocking until one has ended so the next command is `wait && next` rather than a `pgrep` loop written by hand, and ending one |
| `ml-stack-workspace init\|mint\|send\|inbox\|watch\|notes-add\|scratch-new\|claim\|status` | person connection: `connect --code-only --no-project` prints a generic invitation immediately; for another device first `coordinator host`, person-approved cluster `listen`/`pair`, then `connect --remote --code-only --no-project` includes the exact shared authority; agent-issued invites print their approval request ID while waiting. how agents on this machine coordinate without a person relaying text or sharing scratch files: each agent holds its own token (`init` at a terminal, `mint` for a lead or agent) and every message, note and claim is attributed from it, never from what it says. `send` / `inbox` / `wait` / `watch --once` are a durable ordered bus (a lead starts `watch --once` in the background and its exit is the wake-up); `notes-add\|notes-search\|notes-get\|notes-verify` keep decisions, rules, facts and questions with a trust level the service sets (human, test-verified by an allow-listed re-derive command, agent-claimed) and a TTL after which they are stale; `scratch-new\|-ls\|-path\|-rm` give each agent an owner-only folder that refuses paths outside it; `claim\|release\|heartbeat\|who\|claims` own branches, worktrees, ports, files, source areas, install environments and servers until the TTL or the owning pid ends; `quarantine-ls`, `quarantine-release`, `audit-verify` and `status` (with the test-slot queue) are read or human-only. Everything read back is fenced as untrusted data from an agent and carries no authority; writes holding a credential or a term from the private-terms denylist are refused; `--json` everywhere |
| `ml-stack-suite run NAME --seed N` | a measurement run over several seeds and written down whole: the seed, the commit and whether the tree was edited, the wall clock, the peak memory, how busy the card was when it started, and each metric's mean, spread and how many seeds actually produced it. A suite is a function that measures one seed and returns numbers (`@ml_stack.train.suite.register`); `--import MODULE` brings a project's own in, `--set k=v` reaches its arguments, `--out DIR` writes the result after **every** seed, so a run killed in its third keeps the two it paid for, and two runs of one suite take turns on a lock rather than timing each other |
| `ml-stack-speech providers\|transcribe\|say\|regions` | what this machine can hear and say: `providers` lists every engine -- faster-whisper, whisper.cpp, Whisper through transformers, piper, kokoro, the operating system's own voice, Silero and an energy detector that needs nothing installed -- with whether it could run here and which one is picked when none is named; `transcribe FILE` prints the text (`--json` the segments with their times), `say TEXT --out FILE.wav` writes the spoken line, and `regions FILE` the seconds somebody is speaking. `--provider NAME` picks one engine, `--language xx` names the language rather than guessing it. Audio is anything ffmpeg reads |
| `ml-stack-credentials set\|list\|unset\|path` | the tokens and keys the stack reads, found in this order: the environment variable `NAME`, the file `NAME_FILE` names (a mounted secret), the credentials file `~/.ml-stack/credentials.toml` (`ML_STACK_CREDENTIALS_FILE` moves it), Hugging Face's own token file for `HF_TOKEN`, and the values stored with `--keychain`, wrapped under the keystore master key (docs/keystore.md); `set NAME` reads the value from a hidden prompt or stdin (never an argument) and writes the file atomically, mode 0600; `list` prints each name with where it comes from and never a value; a credentials file other users can read is refused until `chmod 600` |
| `ml-stack-setup` | what this machine can do — memory a model may use and whether that survives a reboot, which architectures the installed build reads and how old it is, what is already downloaded, what speech providers answer — and what the stack does without being asked; `--checkouts` adds everything `ml-stack-doctor` checks on its own, in the same command; `--yes` runs the fixes offered; exit 1 when anything is wrong |
| `ml-stack-doctor` | the checkouts (hooks installed, working tree clean, how far ahead of origin, a worktree pinned behind HEAD, whether `import ml_stack` lands in the checkout or a copy), the bench store (runs that read back as nothing, a `measuring.json` whose pid is dead, a log with no run kept from it) and the managed llama.cpp (`current` answers `--help`, the named builds, one older than 14 days) — the checks `ml-stack-setup` leaves for a second command; `--repo PATH` or `$ML_STACK_CHECKOUTS` (none by default) picks the checkouts, `--bench-home PATH` the store, `--yes` runs the fixes it offers; exit 1 when anything is wrong, and never a push |
| `ml-stack runtime ensure\|status\|rollback` | the installed runtime follows the source checkout without waiting for the machine to be idle: ensure builds the checkout's HEAD from a `git archive` into a new immutable tree beside the old ones, smokes it (import in isolated mode, the stamped commit, the workspace CLI help, the Claude hooks against a temporary state root), rewrites every console launcher atomically and selects it; a failed build or smoke leaves the selected runtime alone and is recorded; a selection that is missing, unimportable or below the epoch in packaging/runtime-floor falls back to the newest verified runtime and rebuilds; the background option returns at once, and one build runs at a time under an install claim held by the acting workspace agent; status lists the selected, kept and unmanaged runtimes; rollback selects the newest earlier runtime and holds the commit it left until HEAD moves; the checkout, launcher directory, ref and force options override what is recorded |
| `ml-stack-train-run --recipe R --data DIR --out DIR` | train one recipe from a config file; `--dry-run` is twenty steps that write nothing, `--lora` fits an adapter and `--export-gguf` carries it through to a served file, `--detach` puts the hours in a background log that `status`, `wait` and `stop` follow. `ml-stack-train-run parity` instead of the flags compares this machine's two array backends operation by operation -- reductions, shapes, elementwise maths, every axis argument on more than its default axis -- and prints the largest absolute difference for each, exit 1 if any disagree |
| `ml-stack-decide ask\|eval\|calibrate\|bench\|train\|jevbench` | a decision model picks one of a named set of options and reports a probability for each: `ask QUESTION --state TEXT --option NAME[=DESCRIPTION]` answers one, `ask --state TEXT --noul NAME=Q --choice NAME=Q:A,B --score NAME=Q:LO..HI [--json]` answers several named yes/no, choice and ordinal-score questions about one state with probabilities (`p_true`, per-option, expected value; a failed question abstains with an error and the command exits 1), `eval CASES` and `bench CASES` score backends (`pointer`, `logprob`, `embed`, `rules`) on a JSONL file of labelled cases or on `guards`, the built-in agent-guard set, for accuracy, Brier score, expected calibration error and latency percentiles, and `calibrate CASES --out FILE` fits temperature scaling (and `--isotonic`) on whole groups held apart from the scoring; `export-cases`, `make-cases TOOLS.json` and `check-cases` write, synthesise and read the case format, `list` shows the trained deciders, `fetch --yes` downloads the pinned pointer checkpoint, `train` fine-tunes a decider from labelled cases (`docs/decision-models.md`) and `jevbench` scores the backends on the public JevBench items (opt-in, uses the GPU) |
| `ml-stack-train-decider CASES --out DIR` | fine-tune a pointer-head decision model from labelled cases (a JSONL file, or `guards`): a rank-16 LoRA on a small base model and a pointer head, the options shuffled on every pass, a temperature fitted on groups held apart from training and scoring; `--init strands` continues from the released checkpoint. `DIR` holds `head.safetensors`, `lora/`, `decider.json` with the base pins and file hashes, `manifest.json` with the data hash, splits and metrics, and a `model_card.md` that says when a run is only a pipeline check; the decider is registered by name, and `ml-stack-decide list` shows it and the pointer backend of `ml-stack-decide` uses it by that name |
| `ml-stack-train-tools` | a project's tool schemas → synthetic conversations → a fine-tuned caller → a GGUF, in one command; `--dry-run` prints the plan with counts, `--only` runs one stage, `--ask` has a served model write more questions; `from-bench` builds the same data out of the traces a bench run kept |
| `ml-stack-cluster join\|status\|leave` | one command makes this machine a peer: the checks serving depends on, a llama-server if there is none, the passphrase, the daemon (`--persist` starts it at logon too), and then the devices in the cluster; `status` lists every peer with what it serves, its room, whether it is measuring, the commit it runs and how it updates itself; `leave` undoes it; `--track main` makes this machine follow a branch rather than releases |
| `ml-stack-cluster listen\|requests\|accept\|decline\|nearby\|pair\|revoke\|bootstrap\|share\|fetch\|signing\|peers` | put a new machine in the cluster without downloading anything by hand, and without anyone pushing anything at it: `listen` opens pairing here for a while and asks you with a dialog whose buttons are Decline, Accept as mine and Accept as someone else's (a second dialog then shows a six digit code; `ML_STACK_NOTIFY=console` prints instead, and `accept ID --mine\|--other` / `decline ID` answer from the terminal); the new machine runs `pair --host H` and types the code -- a password-authenticated exchange (the `spake2` package) that fails for a wrong code (three tries) or a machine in the middle, then hands over the cluster key unless `--no-cluster`; `nearby` lists machines open to pairing; `revoke` stops trusting one; `share --dir D` serves files, signed, with a level per file (open, owner for a gated model that only your own devices get once your licence acceptance is recorded, never) and `fetch NAME --from H:P` brings one into staging; `peers` lists, adds, removes or switches off (`off`/`on`) the paired devices that `ml-stack-models pull` and `fetch` ask for a model file before the Hub (the `no-peers` option of those commands or `ML_STACK_NO_PEERS=1` skips them; docs/model-discovery.md); `signing` shows the signing key (kept in the OS keystore) and does export, rotate, revoke and confirm-before-signing only for a person at a terminal; `devices` shows each paired device as lan, tailnet or unreachable and whether Tailscale was found (read-only `tailscale status --json`; a tailnet is a route, the pinned certificate still decides; `--learn` stores a tailnet address only after the certificate matched there); `bootstrap --share DIR` offers the wheel on the LAN for ten minutes to a machine with nothing installed, and `bootstrap --ssh [user@]host --share DIR [--dry-run]` installs over your own ssh keys with a host key typed in full and a fixed script that checks an OpenSSH signature and every SHA-256 first. Everything takes `--json`; docs/onboarding.md has the design and what is not built |
| `ml-stack-mcp` | the same functions, as MCP tools over stdio for an agent to drive -- `serve_*`, `models_*`, `bench_*`, `fleet_*`, `world_make`, `speech_*`, `setup_look`, `doctor`; anything long detaches and returns its log and pid; `--list` prints the tools |
| `ml-stack <command>` | runs any `ml-stack-<command>` listed here (`ml-stack chat ...`, `ml-stack bench sweep ...`, `ml-stack train run ...`); `--list` prints each with the first line of its help; bare, the daemon and your browser on it |
| `ml-stack-graph geocode --graph FILE --cache FILE.json` | every entry that names a place given a point through Nominatim, cached so a place is asked about once, written back onto the node as `lat`/`lon` -- which is what the page's map draws. `--near K` joins each placed entry to its K closest with a `near` edge weighted 1/(1+km), `--out` writes elsewhere than over the graph |
| `ml-stack-graph serve --site FILE` | a rendered graph page (`graph.page.render`) served on loopback as a whole document: `GET /` is the page with `window.GRAPH_LIVE` set so it asks this server rather than nothing, `/export/<path>` a file under `--export DIR` (JSON and HTML by their suffix, anything else as bytes, nothing outside the root), and the ask routes -- `/ask`, `/ask/stream`, `/thread/<name>`, `/ask/model`, `/metrics` -- answered over `--graph FILE` with `--model` leased on the first question (`--model-port` is where it is served), every question and answer kept in `PATH.conversations` beside the corpus `--store PATH` names, never in it (`--conversations-in-store` keeps them in it); `--port` picks the listener. `POST /request` appends the page's change request to `--requests FILE` (`PATH.requests.jsonl` beside the store, or beside `--site` without one) and has the model propose edits for it into the review queue `GET /review` lists and `POST /review` accepts, refuses or undoes (`--review FILE`, `PATH.review.json` by default), an accepted edit landing in `--store`; `/refresh` and `/draft` answer once a subclass gives them stages and a drafter |
| `ml-stack-audit` | every tracked file of a checkout read for a person's details with the pre-commit hook's reader -- names from `NAMES_GRAPH` and `NAMES_SCRAPE`, the allow-lists, the shape rules and the recogniser, asked about card numbers, IBANs and passports as well as people -- printed as a list to look at, exit 1 when there is one; `--staged` is the hook's own check without a commit, `--all` adds the noisy kinds (places, dates, URLs, addresses, driver licences), `--floor` the recogniser's confidence, `--root` another checkout, `--fixtures` the allow-list, `--json` one object per finding. `scripts/encrypted-volume.sh NAME DIR setup\|mount\|unmount` keeps a directory inside an AES-256 sparsebundle on macOS, the passphrase in the login keychain as `NAME-data`; setup with a source directory moves it in and leaves a symlink |
| `ml-stack-bench standard` | the standard sets -- GSM8K (`gsm8k_cot_llama`), MMLU-Pro, IFEval and HumanEval (`humaneval_instruct`, which runs the model's code on this machine) -- through lm-evaluation-harness (the `standard` extra) against any OpenAI-compatible chat endpoint, given its `--url` and `--model` name, under the same measuring lock as a run; `--limit N` scores the first N of each set, the thinking switch (`--think` or `--no-think`) rides in every request and the JSON says which was sent (or `server default`), `--dry-run` prints the `simple_evaluate` kwargs per set, and the `--out` file (`--label` names the configuration) is one JSON per configuration -- score, metric, documents scored and seconds per set -- for a comparison to read |
| `ml-stack-memory` | what the chat agent remembers across sessions, for a person at a terminal (an agent's process is refused): `list`, `show ID`, `add TEXT` (`--kind` preference, machine, result or note; `--source`; `--model`), `confirm ID` (checked under the build in use now), `forget ID` or `forget --all`, `export` as JSON and `stats` (size, limits, facts to re-check, whether the sealed store passed its integrity check); facts about a build or a measurement are marked to re-check after the managed llama.cpp build changes or 30 to 90 days |
